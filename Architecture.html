Backend Modules (picky-server)

🔐 Auth Module
Controllers: sendOTP, verifyOTP, refreshToken, logout
Service: OTP generate/verify, JWT sign, session management
External: Twilio SMS, Redis OTP store (5-min TTL)
📦 Product Module
Controllers: list, detail, search, create, update, delete
Service: pricing with discount, characteristic filtering, Cloudinary image upload via Multer+Sharp
🛒 Cart Module
Controllers: get, addItem, updateQty, removeItem, clear, applyCoupon
Note: Cart in DB for logged-in users; localStorage for guests → merged on login
🧾 Order Module (includes Tracking)
Controllers: checkout, list, detail, updateStatus, addTracking
Tracking flow: Admin enters AWB + courier → status becomes "shipped" → WhatsApp with AWB sent → Customer sees AWB in tracking page
Status states: confirmed → shipped → delivered
statusHistory[]: Each transition logs timestamp for timeline display
🎫 Discount & Coupon Module
Product-level, Category-level, Store-wide, and first_order gift (silent — never shown to customer).
📊 Report Module
MongoDB Aggregation Pipeline → JSON for charts + CSV download via res.attachment()

Middleware Stack (in order)

1. helmet()
Security headers — XSS, CSP, HSTS
2. cors()
Allowlist: client domain (Vercel)
3. express-rate-limit
Global 100/15min • Auth 5/15min • OTP 3/15min
4. morgan + winston
HTTP logging • Error logging to files
5. authenticateToken
Verify JWT • Attach req.user
6. requireRole('admin')
Role-based guard for /admin/* routes
7. zodValidate(schema)
Validates body / params / query
8. globalErrorHandler
Catches all errors → structured JSON

// hooks/useOrderTracking.js
export function useOrderTracking(orderId) {
  return useQuery({
    queryKey: ['order-tracking', orderId],
    queryFn: () => orderService.getTracking(orderId),
    refetchInterval: 30_000, // poll every 30s while shipped
    enabled: !!orderId,
  });
}

🚚 Logistics

Order & Shipping Flow

Complete lifecycle from cart to delivery — manual courier dispatch + WhatsApp notifications.

Full Order Journey

1
Browse & Add to Cart
Browse products, apply filters, add to cart. Guest cart saved in localStorage.
2
OTP Login
Phone → OTP via SMS → Verify → JWT issued. Guest cart merges into DB.
3
Checkout
Enter address, apply coupon, review summary, confirm (COD). First-order gift applied silently.
4
✅ Status: Confirmed
Order created. Stock deducted. WhatsApp sent to customer with order number.
5
Admin Drops at Courier Branch
Admin physically takes parcel to DTDC / ST / Professional / Rathimeena. Courier gives AWB number.
6
🚚 Status: Shipped — AWB Entered
Admin enters AWB + courier in Picky admin panel. Status → Shipped. WhatsApp with AWB sent to customer. Customer sees AWB in Order Tracking page.
7
🎉 Status: Delivered
Admin marks as Delivered. WhatsApp delivery notification sent. user.orderCount incremented.

Branch Naming Rule: feat/client/<feature> or feat/server/<module>/<feature>  |  Commits: feat(order): add AWB tracking endpoint (Conventional Commits)  |  No direct push to main or develop — always PR.

git pull origin develop

git rebase develop   # keep up to date

## Work on your feature...

## Save your progress

## Push your branch

## END OF SPRINT — open Pull Request
# Target: develop (NEVER main)

# Add description + testing steps

Commit Message Format

# Format: type(scope): short description

## Types:
feat     → New feature
fix      → Bug fix
chore    → Maintenance, deps, config
refactor → Code refactoring (no behavior change)
docs     → Documentation only
test     → Adding/fixing tests

## Good examples:
feat(auth): add OTP send via Twilio SMS
feat(order): add 3-step tracking stepper UI
feat(order): add AWB entry + WhatsApp trigger
fix(cart): correct qty validation vs stock
fix(tracking): show correct courier name
chore(deps): upgrade mongoose to 8.x
refactor(order): extract pricing logic to helper

## Bad examples (DON'T DO):
"update stuff"
"fix bug"
"changes"
Sync often: Rebase from develop daily to avoid big merge conflicts. Especially critical when Dev 3 modifies models that Dev 4 depends on.
🔍
Always target develop
PRs must target the develop branch. Never push directly to main. main is only updated by merging develop at release time.
📊
Minimum 1 reviewer
Every PR needs at least 1 team member to review and approve before merging. Rotate reviewers — don't always review the same person.
✅
CI must pass
GitHub Actions runs lint + tests on every PR. Green checkmark required before merge. Fix any lint errors locally before pushing.
📝
PR Description required
Every PR must have: What changed, Why, How to test it. Use the PR template if available.
🔓
No .env in commits
Never commit .env files. Only commit .env.example. Secrets go in GitHub Secrets or Vercel/Render environment settings.
🌐
API Contract first
Dev 3/4 must define the API response shape in README or api.md before implementing. Dev 1 mocks it while waiting so frontend and backend work in parallel.
